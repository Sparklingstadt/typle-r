## Release workflow

Read `docs/release-workflow.md` before publishing changes. The required order is
PR → merge (squash by default, ordinary merge when the user asks) → post-merge verify → GitHub Release → Vercel production deploy.
Since v2.38.1 GitHub Actions takes no part in it (the only workflow left, `docs-deploy.yml`, publishes `api-docs/` on
request): the verify, the Release and the deploy are done by hand on the user's Mac, one release at a time, in the
order below. Do not push directly to main. Prepare a PR with a new stable package version. A failure must be fixed or
retried at the failed stage, never bypassed.

Every PR takes a version no other commit has used: before `npm version`, check
`git tag` and the GitHub Releases, and bump again if the PR's version was taken
by a PR merged in the meantime.

### Verify

`npm run verify` (`scripts/verify.cjs`) runs every check in this order and stops at the first failure:
`npm run db:migrate` on the local database (`DATABASE_URL` in `.env.local`; the DB tests add rows under random
owners and delete them), `node --test tests/migrate.test.cjs`, `gofmt -l .` (empty), `go vet ./...`,
`GOTOOLCHAIN=go1.25.0 go run honnef.co/go/tools/cmd/staticcheck@v0.7.0 ./...`, `go test ./...`, `npm run typecheck`,
`npm test`, `npm run lint`, `npm run knip`, `npm run build`, `npm run test:e2e`, and `npm run docs:build` /
`npm run docs:check` in `api-docs/`. `npm run verify -- --fast` leaves out the end-to-end tests and the API docs while
working; run it in full before opening the PR. It needs Docker (the local PostgreSQL), Go 1.25 and Node.js 24, so a
cloud session cannot run it: say so and hand it to the user.

### Release and deploy (the user's Mac)

After the merge, on the main commit, after the user confirms each step that publishes:

1. `git switch main && git pull --ff-only`. Confirm HEAD is the PR's squash or merge commit and `git status` is
   clean, then run `npm run verify` in full. Do not publish while it fails: fix it in a new PR with a new version.
2. Create the GitHub Release on that commit: tag `v<package.json version>`, non-draft, non-prerelease, notes
   generated by GitHub. Never move a tag or reuse a version.
   ```bash
   gh release create "v$(node -p "require('./package.json').version")" --target "$(git rev-parse HEAD)" --title "v$(node -p "require('./package.json').version")" --generate-notes --latest
   ```
3. Deploy that same commit with `vercel deploy --prod --yes` from the same checkout (it needs Vercel credentials;
   cloud sessions have none, so hand this step to the user with the exact commands). Wait until the production
   domain serves the new deployment, then run `npm run check:production` (`scripts/check-production.cjs`), which
   checks `https://typle.sparklingstadt.com` and the Vercel domain `https://typle-r-six.vercel.app`.
4. When `api-docs/` changed, run the "Docs deploy" workflow on main (`docs-deploy.yml`).

## コードとコミットの規約

- `src` の層と依存の向きは README の「コードの構成」にあります。`eslint.config.mjs` が
  `src/core`・`src/plugins` からの逆向きの import と、画面から保存先プラグインへの import をエラーにします。
- squash merge・普通のマージのコミットのタイトルと PR のタイトルは、変更を日本語の1文で書き、末尾に半角の
  `(vX.Y.Z)` を付けます。`fix:` などの接頭辞は付けません。PR 番号は squash merge で付き、普通のマージでは手で付けます。PR の途中のコミットは内容だけを書き、`(vX.Y.Z)` は付けません。

## 出力の言語

ユーザーへの返答、PR のタイトル・説明、コミットメッセージ、`docs/`・README・CHANGELOG は日本語で書くこと。
コードのコメントと識別子、`CLAUDE.md` の Release workflow の節のように英語で書かれている箇所は、
周りに合わせて英語で書く。
