## Release workflow

Read `docs/release-workflow.md` before publishing changes. The required order is
PR → merge (squash by default, ordinary merge when the user asks) → post-merge verify → GitHub Release → Vercel production deploy.
Do not push directly to main or run manual release/deploy commands. Prepare a PR
with a new stable package version; GitHub Actions owns release and deployment.
Cloud sessions do not need Vercel CLI or Vercel credentials. A failure must be
fixed or retried at the failed stage, never bypassed.

Every PR takes a version no other commit has used: before `npm version`, check
`git tag` and the GitHub Releases, and bump again if the PR's version was taken
by a PR merged in the meantime. Never commit with `[skip ci]` to get around the
order.

### Exception: GitHub Actions blocked by billing

Only when the jobs were never started because of GitHub billing (the check's
annotation says "The job was not started because recent account payments have
failed or your spending limit needs to be increased"), the release is done by
hand instead. Any other CI failure follows the rule above. Keep the same order
and one release at a time:

1. Run the checks `verify` would have run, on the PR head, in its order:
   `node --test scripts/ci/release.test.cjs`, `npm run db:migrate` on a test DB,
   `gofmt -l .` (empty), `go vet ./...`,
   `GOTOOLCHAIN=go1.25.0 go run honnef.co/go/tools/cmd/staticcheck@v0.7.0 ./...`, `go test ./...` (with
   `TYPLE_TEST_DATABASE_URL` on that DB), `npm run typecheck`, `npm test`, `npm run lint`, `npm run knip`, `npm run build`,
   `npm run test:e2e`, and `npm run docs:build` / `npm run docs:check` in
   `api-docs/`. Report any check that could not be run; do not merge on a failure.
2. Merge the PR as in the required order (never push to main directly), after the user confirms.
3. Create the GitHub Release on the squash or merge commit: tag `v<package.json version>`,
   non-draft, non-prerelease, notes generated by GitHub
   (`generate_release_notes`). Never move a tag or reuse a version.
4. Deploy that same commit to production with `vercel deploy --prod` from a
   machine that has Vercel credentials (the user's Mac; cloud sessions have none,
   so hand this step to the user with the exact commands). Then make the checks of
   the `deploy` job in `.github/workflows/ci.yml` against
   `https://typle.sparklingstadt.com` (and the Vercel domain `https://typle-r-six.vercel.app`
   where the deploy job checks it), and publish `api-docs/` as `docs-deploy` does.
   This is the only case in which `api-docs/` is published from a local
   `wrangler` (the version pinned as `WRANGLER_VERSION` in `docs-deploy.yml`).

## コードとコミットの規約

- `src` の層と依存の向きは README の「コードの構成」にあります。`eslint.config.mjs` が
  `src/core`・`src/plugins` からの逆向きの import と、画面から保存先プラグインへの import をエラーにします。
- squash merge・普通のマージのコミットのタイトルと PR のタイトルは、変更を日本語の1文で書き、末尾に半角の
  `(vX.Y.Z)` を付けます。`fix:` などの接頭辞は付けません。PR 番号は squash merge で付き、普通のマージでは手で付けます。PR の途中のコミットは内容だけを書き、`(vX.Y.Z)` は付けません。

## 出力の言語

ユーザーへの返答、PR のタイトル・説明、コミットメッセージ、`docs/`・README・CHANGELOG は日本語で書くこと。
コードのコメントと識別子、`CLAUDE.md` の Release workflow の節のように英語で書かれている箇所は、
周りに合わせて英語で書く。
